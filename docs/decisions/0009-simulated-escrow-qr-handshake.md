# ADR-0009: simulated escrow with a real QR handshake

- **Status:** Accepted (2026-09-08, Phase 3)
- **Context:** The pitch's step 4 — "escrow payouts split via QR-code handshake at the doorstep" — requires payment infrastructure the demo cannot (and legally should not) exercise. But the escrow *contract* is the product's trust story and must be demoable end-to-end.
- **Decision:** A server-side escrow record tracks `held → in_transit → released` (`lib/escrow.ts`, keyed to the immutable published snapshot). Dispatch generates a random `FARMIT-XXXXXXXX` delivery code; the QR is rendered server-side as SVG (`qrcode` package — the demo's only new runtime dependency, confined to `apps/web`). Release **requires the code**; the demo's "simulate courier scan" button supplies it client-side, exactly what a real courier scanner app would present to the endpoint. Splits are computed only from the server-held snapshot (`lib/snapshots.ts`), never client payloads. On release the split (farmer / miller / transporters / platform / GST) is returned and must sum exactly to the escrow total.
- **Consequences:** Full judge-visible lifecycle with verifiable guards (wrong code, double release, hold-before-publish all fail closed). Demo-local store resets on restart — at pilot, records map to a licensed payment-gateway escrow/split settlement; `EscrowRecord` is the contract. The `qrcode` dependency is an accepted exception to the zero-dep policy for packages.
- **Alternatives rejected:** client-held split data (spoofable — violates ADR-0002's principle); smart contracts (out of scope, no chain in the stack); skipping QR and using buttons only (loses the deck's signature handshake).
